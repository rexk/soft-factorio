Build it in stages on one ledger per repository, starting with the factory's own evals

Key: metricsDate: 2026-11-06Author: an agent, for the maintainerStatus: design brief; A2 picked 2026-11-06Source: product.html (approved), research.md, this repository

Recommended: A2. Each repository keeps one append-only ledger of numbers and readings, tied to factory versions. Stage 1 fills it from the factory's own eval runs, which already produce the data. Stage 2 lets an adopting repository compute its numbers from its git history and pull requests. Stage 3 adds the optional quick answer. Each stage is its own PR, and each delivers something useful by itself.

Approaches

A1. Factory ledger only

Effort S Risk low

The eval runner appends each pass's numbers, with the factory version, to a committed append-only ledger. A compare command shows two or more versions side by side, as plain data and as a page. Readings are appended to the same ledger.

  • Reuses: run.py results, factory_version(), html-for-humans.
  • Misses: B2 and B4. Adopting repositories get nothing.

A2. One ledger per repository, in stages (recommended)

Effort M overall Risk medium in stage 2

A1 is stage 1. Stage 2 ships the same tool and a small metrics skill into adopting repositories. It computes their numbers on demand from git, the manifest's history, and their PRs (merged or not, review rounds, time to merge, reverts, Lessons rows), split by factory version, with the time before the factory as its own period. Stage 3 adds the optional quick answer at the end of a task.

  • Reuses: everything in A1, the manifest, the retro tables, the fake gh.
  • Delivers all of B1–B9. Each stage is useful by itself.

A3. Git notes or issues

Effort S Risk high

Attach numbers and readings to factory commits as git notes, or post them as issues.

  • For: notes attach to a version natively.
  • Against: git doesn't push or fetch notes by default, and GitHub doesn't show them, so agents and authors miss them (B5, B9). Issues live outside the repository's files, which strains B9 and needs a network.

Recommendation

R1. A2. It is the only approach that reaches adopting repositories, which the maintainer asked for. Its first stage is exactly A1, so we get evidence about the factory within a day and learn what a useful comparison looks like before building stage 2. One ledger format serves both the factory and adopting repositories, so readings work the same way everywhere (B7).

Test plan

Every test is a unit or integration test that python3 tools/check.py runs, locally and in CI. Git repositories are built in temporary folders, and PRs come from the fake gh.
